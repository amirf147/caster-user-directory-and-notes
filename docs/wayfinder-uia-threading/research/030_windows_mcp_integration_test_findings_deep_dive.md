# Ticket 030 Deep Dive: Windows-MCP Integration Test Findings

This document contains the findings from investigating the issues discovered during the `Windows-MCP` persistent integration test (Ticket 030).

## 1. Thread Hanging & Teardown Failures (Root Cause)

**Observation**: During the test loop, the process frequently froze and required the user to send multiple `Ctrl+C` interrupts to force close the server.

**Root Cause**: The issue originates entirely from our test script (`test_mcp_standalone.py`), not the server itself. 
- When the user presses `Ctrl+C` while the script is in `time.sleep()`, Python raises a `KeyboardInterrupt` exception.
- Because the script lacks a `try...finally` block, the exception immediately halts execution before reaching `proc.terminate()`.
- Consequently, the `uvx windows-mcp serve` child process is left orphaned in the background, still holding onto system resources and COM threads.
- When the user runs the test again, or tries to interact with their system, the orphaned server conflicts or hangs.

**Resolution**: This is a trivial fix. All Python clients invoking the server via `subprocess.Popen` must ensure graceful teardown by wrapping the execution in a `try...finally` block that guarantees `proc.terminate()` is called on exit.

## 2. Workspace / Virtual Desktop Isolation (Root Cause)

**Observation**: The server only matched and switched to windows located on the *current* active workspace (virtual desktop).

**Root Cause**: In `windows_mcp/desktop/service.py`, the `get_controls_handles()` method uses the Win32 API `win32gui.EnumWindows(callback, None)`. 
Inside the callback, it enforces strict filtering:
```python
if (
    win32gui.IsWindow(hwnd)
    and win32gui.IsWindowVisible(hwnd)
    and is_window_on_current_desktop(hwnd)
):
```
Because of `is_window_on_current_desktop(hwnd)`, the server is architecturally limited to enumerating windows on the active desktop. Windows on other virtual desktops are completely invisible to its enumeration logic.

## 3. Tab Matching & Fuzzy Matching Flaws (Root Cause)

**Observation**: When attempting to switch to a specific browser tab (e.g., "LinkedIn - Waterfox"), the server failed to accurately match the exact tab title and instead randomly picked any available Waterfox window.

**Root Cause**: 
The `switch_app` tool relies on `_find_window_by_name()`, which performs fuzzy matching (`fuzzywuzzy.process.extractOne`) against a list of window names generated by `get_windows()`. 

However, `get_windows()` only enumerates **top-level windows** returned by `win32gui.EnumWindows`. It does *not* traverse the UI Automation tree to find individual background tabs within a browser window. 
- If the user tries to switch to "LinkedIn - Waterfox", but that tab is inactive in the background of a window currently titled "YouTube - Waterfox", the top-level window title is "YouTube". 
- The fuzzy matcher never sees the string "LinkedIn". Instead, it loosely matches "Waterfox" against "YouTube - Waterfox" and randomly switches to that window.

## Conclusion & Recommendation

`Windows-MCP` relies heavily on standard Win32 API top-level window enumeration (`EnumWindows`) rather than deep UI Automation tree traversal for its application switching logic. Furthermore, it explicitly limits itself to the current virtual desktop.

**Recommendation**: 
While the hanging issue is a simple client-side fix, patching the Python server to support cross-workspace window matching and deep UI Automation tree tab enumeration would require a substantial and complex rewrite of its core `get_windows` logic. 

Given the underlying Python COM latency and thread pumping vulnerabilities previously identified (see Ticket 028), it is **highly recommended to abandon the Python server** for Window/Tab switching. We should proceed with building a custom C# `.NET MCP Server` where cross-desktop detection and deep UI Automation traversal can be implemented natively, safely, and performantly.
